# 初期グリッド推定とFinder自動設定

[English](ZXING_CPP_INTEGRATION.en.md) | 日本語

本文書は、Android版における初期QRグリッド推定の現行動作、検証条件、既知の限界をまとめます。対象はZXing-C++による境界検出、格子周期による補助推定、2つのFinderによる補助推定、Finder役割の自動設定です。いずれも編集可能な開始値を提供する処理であり、修復結果の正しさを証明するものではありません。

## 処理の境界

- Androidは既存のワーカースレッドからJNI経由でZXing-C++ 3.1.1を呼び出します。
- 境界からモジュールへの変換と候補検証は共通コードで実装します。
- 対象はQR Code Model 2のバージョン1～40です。
- ネイティブ側の復号文字列は修復結果に使用しません。
- iOSのネイティブ検出アダプターは未実装です。

## 推定順序

新規画像を読み込むと、次の順に試します。

1. ZXing-C++が返した境界を検証します。
2. 画像の周期性から矩形のモジュール格子を推定します。
3. どちらも失敗した場合、個別検出した2つのFinderから幾何を推定します。
4. すべて失敗した場合、バージョン1と既定の四隅を表示し、手動調整へ進みます。

採用した経路と初期バージョンは取り込み履歴へ記録します。修復では画面上の四隅と選択バージョンをユーザーが確認した入力として扱うため、推定後も確認が必要です。

## 通常画像と反転画像

各境界は通常・反転の輝度で調べます。両方が検証に通る境界は曖昧として採用しません。周期推定と2つのFinderによる補助推定でも両方を調べます。双方で推定できた場合は、バージョン・四隅の順序が一致し、対応する各隅が0.25モジュール以内である必要があり、確定した通常・反転の判別が矛盾する場合は棄却します。周期推定が競合した場合は自動推定を見送り、2つのFinderによる経路へ進みません。周期推定だけでは通常・反転を確定せず、ネイティブまたは2点推定のFinder役割を検証できた場合だけ判別結果を保存します。

## ZXing-C++境界の検証

単一のネイティブ境界について、バージョン1～40と論理回転4通りを検査します。座標は有限かつ画像内で、四角形は凸である必要があります。Finderとタイミングパターンの不一致率はそれぞれ20%以下とします。両スコアを0.55対0.45で重み付けし、次候補との差が0.03未満の場合は曖昧として採用しません。

複数境界は個別に検証します。全ペアでバージョンと論理向きが一致し、対応する各隅が0.25モジュール以内の場合だけ統合します。許容距離には各隅における両候補の小さい方のモジュール幅を使います。代表候補はFinder役割の自動設定条件を満たすものを優先し、次に四隅の距離合計が最小のものを選びます。座標は平均せず、重複検出数を確度へ加算しません。

未検証の境界、異なるバージョンや論理向き、空間的に別のQRが含まれる場合は統合しません。ネイティブ境界を採用・統合できない場合や、JNIの読み込み・実行に失敗した場合は、格子周期による補助推定へ進みます。

## 格子周期による補助推定

輝度勾配を直交する2組のedge方向へ分け、投影したedgeが等間隔の格子境界へ揃う位相とモジュール間隔を探索します。半周期などの高調波が同程度に一致する場合は、基本周期を優先します。

両軸のモジュール間隔が整合し、確実な黒画素による外周が概ね正方形で、21～177の許可寸法と一致する場合だけ、`dimension = 17 + 4 × version`から初期バージョンを設定します。大きな灰色損傷や背景の孤立暗画素は、確実な黒の外周証拠から除外します。

周期推定だけではFinderの役割を自動設定しません。

## 2つのFinderによる補助推定

周期推定も失敗した場合、個別検出したFinderから、概ね相似変換で扱えるバージョン2以上の仮の幾何を作ることがあります。Finderのモジュール幅、軸方向、模様、白い区切りを検証します。ZXing-C++が複数境界を返した場合は、この経路を使用しません。

対角のFinder 2点については、横・縦のタイミングパターンから、観測した右上・左下の役割を位置合わせパターンなしで判定できます。各軸で次を要求します。

- 8セル以上かつ全長の60%以上を判定できること。
- 黒と白の観測がそれぞれ3セル以上あること。
- 不一致率が5%以下であること。
- 中心と上下左右0.2モジュールの計5位置ですべて同じ条件を満たすこと。
- 白い区切りの検証に合格すること。
- 競合候補とのスコア差が0.12以上あること。

不明セルは一致に数えません。タイミングだけで役割を確定できない場合でも、右下の位置合わせパターンを検証できれば、役割を指定せず四隅だけを仮設定することがあります。バージョン1はタイミングセル数が不足するため対象外です。隠れたFinderを観測済みとは扱わず、強い透視変形には対応しません。

## Finder役割の自動設定

ZXing-C++由来の採用格子は、次のすべてを満たす場合だけ、左上・右上・左下のFinder中心と論理役割を自動設定します。

- 各Finderの49セル中、不一致が2セル以下。
- 各Finderの白い区切り15セル中、不一致が1セル以下。
- タイミングパターンの不一致率が5%以下。
- 不採用候補も含む次候補とのスコア差が0.08以上。
- すべての辺で1モジュール当たり2画素以上。
- 中心から上下左右へ0.25モジュールずらした照合でも、各Finderの不一致が2セル以下。

これらは保守的な構造ヒューリスティックであり、確率ではありません。自動設定は新規画像の取り込み時だけ実行し、履歴へ記録します。保存した作業を再開するときは再推定しません。設定済みFinderをすべて解除すると、四隅とセル編集を残したまま論理向きも未確定へ戻します。

2つのFinderによる経路には前節の別条件を使います。周期推定由来の格子、条件を満たさないネイティブ格子、統合できない複数境界では役割を自動設定しません。

## 保存済み検証データ

保存済みの合成画像による調査は、正例240件と負例24件を含みます。寸法が一致し、すべての隅が0.5モジュール以内の場合を正解格子とします。

- 正例240件中224件で正解格子を得ました。
- 正解格子の内訳はZXing-C++由来164件、周期推定由来60件です。
- Finderが1個、2個、3個欠けた計36件は、すべて周期推定で維持しました。
- 負例3件に既存の周期推定候補がありました。候補があることは復号成功を意味しません。
- 周期推定単独では正例240件中140件が正解格子でした。
- 3つのFinderの自動設定条件は128件を設定し、調査基準では128件すべての役割と位置が一致しました。負例の自動設定は0件でした。

これらは保存済み合成コーパスに対する回帰確認であり、独立した性能保証ではありません。周辺点の検証条件は、中心点だけの条件で生じた誤差を観察した後に選びました。保存座標による調査は、Android上のJNI実行、速度、実写での誤設定率、復元文字列の正解率を測定していません。

## 再実行

[検出調査の手順](../tools/detector-study/README.md)に従って`build/detector-study/work`を用意した後、次を実行します。

```sh
./gradlew -p tools/detector-study installDist
tools/detector-study/build/install/qr-detector-study/bin/qr-detector-study initial-grid \
  build/detector-study/work/corpus build/detector-study/work/results/zxing_cpp.jsonl \
  build/detector-study/work/initial-grid.jsonl
build/detector-study/venv/bin/python tools/detector-study/evaluate_initial.py \
  build/detector-study/work/corpus build/detector-study/work/initial-grid.jsonl \
  build/detector-study/work/initial-grid-summary.json
```

測定結果を更新する場合は、固定的な製品性能として示さず、対象コミット、fixture、成功条件、関連する探索上限を明記します。

## 依存関係と配布

Android版はMaven Centralの`io.github.zxing-cpp:android:3.1.1`を固定指定します。AARには`arm64-v8a`、`armeabi-v7a`、`x86`、`x86_64`のネイティブライブラリとJNI用consumer ruleが含まれます。ライセンス通知はApache-2.0のZXing-C++、BSD-3-Clauseの`libzueci`、UTF-8変換コード、LLVM libc++例外を対象とします。

この統合はインターネット権限、外部送信、署名設定を追加しません。依存物のハッシュ、ABI検査、推移依存の確認は[native-dependency-review.json](detector-study/2026-09-18/native-dependency-review.json)に記録しています。リリース判定には過去のテスト件数ではなく、現行のビルド・公開前検査を使用します。
