| 修復前 | 修復後 | 補完箇所 |
| --- | --- | --- |
| ![不規則な9つの穴がある合成QR](before.png) | ![修復後のQR](after.png) | ![補完したセルを青色で表示](details.png) |

この合成例では、841セル中478セル（56.8%）が不明です。[記録された結果](result.json)では、元のQRコードと一致する候補が1つ得られ、次のテキストを復元できました。

```text
QRevy app: recovered QR.
```

## 試す手順

「テキスト行列を読み込む」で[before.txt](before.txt)を開き、修復前設定で次の値を指定します。入力にはテキストファイルを使ってください。上の画像は損傷と結果を示すものです。

| 設定 | 値 |
| --- | --- |
| QRバージョン | 3 |
| 誤り訂正（ECC）レベル | M |
| データマスク | 自動 |
| フォーマットbitの誤り上限 | 自動（6bit） |
| 単一セグメントの仮定 | ON |
| 優先探索のセル数上限 | **5**（初期値は4） |
| データ・ECCの誤り上限 | 0bit（完全一致） |
| 部分bit探索・自由度の上限 | 12bit |

ファイル内の不明な5セルには、優先探索用の`*`が記入済みです。この指定を保ち、四角い位置検出パターン（Finder）の役割を確認します。未指定なら少なくとも1つ指定してから「修復」を実行してください。操作は[ユーザーガイド](../../USER_GUIDE.ja.md)を参照してください。

比較実行では、単一セグメントの仮定がOFFでも元と一致する候補が1つ得られています。仮定をONにして5つの`*`を通常の`?`に置き換えた場合は、候補が得られていません。JSONには、各条件の候補数、探索の完了状況、省略の診断を記録しています。

記録された実行では、修復後のセル配置と内容が元のQRコードに一致しています。ただし、候補が1つ得られても、ほかの答えがないとは限りません。また、この欠損率は一般的な修復限界を示すものではありません。画像はこのプロジェクト用に独自に生成したものです。

[生成スクリプト](../../../scripts/generate-bullet-hole-example.py)は、Git履歴に依存せず修復ソースを識別するため、`core_source_sha256`を記録します。対象は`shared/src/commonMain`、`androidApp/src/main/java/io/github/earthdiver/qrrepair/core`、およびZXingのペイロード解析用ブリッジがある`androidApp/src/main/java/com/google/zxing/qrcode/decoder`内のKotlin・Javaファイルです。各ファイルのSHA-256とリポジトリ相対パスをパス順に並べた一覧をハッシュ化します。
