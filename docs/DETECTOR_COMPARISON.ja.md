# QR 位置・格子推定ライブラリの実測比較

2026-09-17、Linux x86-64 / Intel Core Ultra 7 258V 上で実行。
指定順の **ZXing Detector → quirc・BoofCV → ZXing-C++ → OpenCV の通常方式・ArUco 方式**を比較した。

今回の合成画像では、**格子推定の成功数は ZXing-C++ が最多、軽量な追加候補として quirc が有望**だった。
quirc と BoofCV を追加した段階で相補的な効果が大きく、その後の OpenCV 追加には復元成功数の上積みがなかった。
一方、復元結果は濃淡推定にも強く左右された。検出器の採用判断と、後段の濃淡判定・誤復元防止の改善を分けて考える必要がある。

アプリへの組み込みは行っていない。比較コードは独立した Gradle/JVM・Python ツールで、アプリの依存関係や動作は変更していない。

## 指定順で追加した結果

既存の `StandardQrDecoder` を先に使い、読めなければ既存の `GridPeriodicityEstimator` と共通復元処理を使う構成を出発点にした。
これは既存部品を用いた実験用の自動処理であり、現在の UI、手動編集やすべての探索機能を再現した数字ではない。
通常読み取りだけでは 150/240 件が正解だった。

| 追加段階 | 自動濃淡推定での正解数 / 240 | 前段からの増加 | 固定濃淡設定での正解数 / 240 |
|---|---:|---:|---:|
| 既存の通常読み取り＋周期推定 | 180 | — | 198 |
| ＋Java ZXing Detector | 180 | 0 | 198 |
| ＋quirc、続いて BoofCV | 203 | +23 | 218 |
| ＋ZXing-C++ | 206 | +3 | 218 |
| ＋OpenCV 通常、続いて ArUco | 206 | 0 | 218 |

正解集合の和に加えて、「最初に解析済み文字列が返った段階で止まる」単純なフォールバックも評価した。
このコーパスでは両者の正解数が一致し、フォールバック全体の誤答は両設定とも 0 件だった。
ただし各検出器の出力を個別に復元すると誤答があり、単純な採用条件の安全性が証明されたわけではない。
既存の通常読み取りで先に正解できたことが、今回の誤答を回避する一因になっている。

## 位置・格子の精度と API 実行時間

正解格子は、位置の RMS 誤差が 0.5 モジュール以下で、格子寸法も一致した件数。
位置だけの合格数と共通順位付け後の格子合格数は今回一致し、正解格子はすべて第1候補にも入っていた。

| 方式 | 正解格子 / 240 | 検出時間中央値 ms | 95%点 ms | 既存構成へ単独追加した場合の追加正解数※ |
|---|---:|---:|---:|---:|
| 既存の周期推定 | 140 | 21.308 | 40.645 | — |
| Java ZXing Detector 3.5.4 | 150 | 0.560 | 0.801 | 0 |
| quirc | 152 | 0.845 | 1.407 | 15 |
| BoofCV 1.1.4 | 172 | 1.559 | 2.373 | 19 |
| ZXing-C++ 3.1.1 | **188** | **0.226** | **0.416** | **24** |
| OpenCV 4.12 通常 | 150 | 7.832 | 10.993 | 10 |
| OpenCV 4.12 ArUco | 162 | 3.523 | 8.743 | 14 |

※自動濃淡推定の既存構成 180 件に対する、正解集合の追加件数。指定順での累積増分とは異なる。

時間はファイル読み込みを除いた API 呼び出し・入力変換・候補抽出のコスト。
各画像3回の中央値を集計し、事前に10回ウォームアップ、検出器は逐次実行した。OpenCV は1スレッド。
BoofCV と ZXing-C++ の使用 API は内部でデコードも試みるため、純粋な検出アルゴリズム同士の同一条件比較ではない。
Android/iOS 実機の速度、初回ロード時間、APK 増分は未測定。

## 得意条件と限界

- **quirc**：今回の強い透視変形で格子合格 8/12 件。BoofCV は4件、ZXing-C++ は8件、Java ZXing と OpenCV 2方式は0件だった。一方、影と余白なしでは quirc は0/12件。調整なしの今回の入力・API条件に限った結果である。
- **BoofCV**：影・低コントラスト・複合劣化で各12/12件の格子を推定。quirc を補完した。ただし Java ランタイムへの依存と依存パッケージの大きさを検討する必要がある。
- **ZXing-C++**：影・低コントラスト・小さいモジュール・余白なし・複合劣化で各12/12件。今回の検出性能とデスクトップ API 時間では最有力。
- **OpenCV**：ArUco 方式は通常方式より格子成功数が多かった。先行方式と重なる成功が多く、指定順では復元成功の上積みがなかった。
- **既存の周期推定**：Finder を1個・2個・3個消した各12件、計36件で格子推定に成功。外部6方式はこの36件で全滅した。損傷 QR 向けに既存方式を維持する根拠になった。

QR を含まない24画像では、周期推定が3画像に候補を返し、外部方式は0画像だった。最終的な文字列の誤出力はなかった。
負例が少ないため、これを一般的な誤検出率として扱わない。

## 濃淡設定による差と誤復元

すべての検出器に同じ `MatrixSampler` と `RecoveryEngine` を接続した。
「自動」は既存の `InitialThresholdEstimator`、「固定」は blackMax=96 / whiteMin=160。
両方とも既存の既定の局所適応処理を使用する。

| 格子供給元 | 自動：正解 / 誤答 | 固定：正解 / 誤答 |
|---|---:|---:|
| 周期推定 | 68 / 3 | 140 / 0 |
| Java ZXing Detector | 73 / 3 | 132 / 1 |
| quirc | 56 / 3 | 135 / 0 |
| BoofCV | 86 / 3 | 136 / 1 |
| ZXing-C++ | 96 / 3 | 152 / 1 |
| OpenCV 通常 | 64 / 3 | 117 / 0 |
| OpenCV ArUco | 65 / 2 | 132 / 0 |
| 正解格子を与える対照実験 | 130 / 3 | 204 / 0 |

この表は通常読み取りを先行させない、共通の復元処理単体の結果。
したがって、例えば quirc の56件は quirc 自身のデコード能力を表さない。

正解格子を与えても、自動設定では清浄画像12件中6件の復元に失敗した。
一部画像で自動閾値が blackMax=3 / whiteMin=132 となり、局所適応後の黒セルを未知として扱いやすくなっていた。
固定設定で大きく改善するため、検出器だけで解決できない制約がある。
これは合成画像・所定の探索上限を用いた観察であり、アプリの全操作条件に対する不具合断定ではない。
固定値の方が実写でも優れる、という結論でもない。

自動設定の正解格子対照実験でも、白い損傷パッチがある3画像で元の文字列と異なる解析結果が出た。
例えば `v3-s0-white_data_patch` の正解 `Q3S0TEST` に対し `ZOJ-SO+W` が返った。
固定設定でも、Java ZXing・BoofCV・ZXing-C++ の共通復元処理で各1件の誤答があった。
いずれも成功には数えていない。各ライブラリ自体がこの文字列を誤デコードしたことを意味しない。

復元は1候補あたり cancellation check 10,000回、最大4候補で打ち切る。
候補の向き、未知セル、探索予算、採用条件の影響を含むため、正解格子対照も全復元能力の上限ではない。
RS が成立することや、文字列として解析できることだけを自動採用の根拠にしない設計が引き続き必要。

## 再現条件と出力

240正例 = バージョン1/3/7 × 4種類の文字列・向き × 20条件。
ECC H、通常極性の Model 2。12種類の内容から派生した相関のある合成画像であり、240種類の独立した実写ではない。
回転、透視変形、ぼけ、影、低コントラスト、小モジュール、余白なし、周辺文字、Finder 欠損、データ損傷等を含む。
通常512×512、モジュール7画素、小モジュール条件は2画素。別途24負例。
ユーザー提供画像は一切使用していない。

検出器には正解文字列・位置・バージョンを渡さない。

## 容量・ライセンスと採用判断

今回ビルドした quirc の Linux 共有ライブラリは **38,464 bytes**（約37.6 KiB）。ISC ライセンス。
これは Android/iOS バイナリの容量ではないが、コンパクトさの参考になる。

BoofCV 本体は Apache-2.0 だが、今回の構成には **LGPL-2.1 の trove4j** が推移依存に含まれた。
今回の JVM 配布物は全 jar 合計約16.8 MiB。ただし Kotlin、ZXing、測定コード等も含むため、BoofCV 単独の容量ではない。
Python/JVM を含むプロセスの最大 RSS も記録したが、ライブラリ単体のメモリとしては比較できない。
詳細は[依存関係・ライセンス調査](../tools/detector-study/DEPENDENCIES.md)。製品の配布依存は変更していない。

今回の結果に基づく次の優先順位は、**軽量な quirc と検出範囲の広い ZXing-C++ を組み込み候補として残し、既存周期推定を併用すること**。
BoofCV は有力な比較基準だが、実際に必要な依存範囲と Android/iOS への接続コストを確認したい。
OpenCV は今回の用途だけで新規追加する優先度が低い。
採用前には実機計測と、独立した追加コーパスでの濃淡設定・候補採用条件の評価が必要。
